# Plan: M0.4: Boundary validator

- **Spec:** #16
- **Requirement IDs:** BND-07 (scaffold only), BND-06 (file location)
- **Status:** approved

## Approach

Boundary files live in `data/boundaries/`, as `*.geojson` at any depth, so M1 can add one subfolder per level (resolves the Spec's flagged concern). `scripts/validate-boundaries.ts` exports `validateBoundaries(dir)`, which returns a list of errors, and `run(dir)`, which prints them and returns an exit code. A file fails if it isn't JSON, its `type` isn't `FeatureCollection`, `features` isn't an array, or any feature's `type` isn't `Feature`. A missing or empty folder passes. The script uses only `node:fs` and `node:path`, and Node 24 strips the TypeScript types itself, so there's no new dependency and the CI job needs no `npm ci`. A new `boundaries` job in CI runs it on every PR; it becomes required in M0.5.

## Alternatives considered

- **A GeoJSON library such as `@turf/boolean-valid`:** it adds a dependency for checks that M1 decides on. Left until M1.

## Risks

- **ESM detection warning:** with no `"type"` in `package.json`, Node may warn when it treats the `.ts` file as ESM. If it does, rename to `.mts` and widen the Vitest globs (recorded as a deviation).
- **`import.meta.main` under Vitest:** if Vitest sets it, importing the script would run it. The test checks that importing has no side effects.
- **Fixtures picked up as real data:** fixtures sit under `scripts/__tests__/`, never under `data/boundaries/`.
