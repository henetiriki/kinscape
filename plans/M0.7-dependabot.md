# Plan: M0.7: Dependabot and vulnerability upgrades

- **Spec:** #26
- **Requirement IDs:** none (engineering-only; see Spec's flagged concerns)
- **Status:** approved

## Approach

Add `.github/dependabot.yml` with npm and github-actions entries, weekly. Groups only apply to version updates (the default `applies-to`), so security PRs stay individual and open as soon as an advisory lands. A dependency joins the first group it matches, so the coupled groups come first and take majors too; the production and development groups take only minor and patch, which leaves each other major as its own PR. `versioning-strategy: increase` keeps exact pins exact.

Groups: `next` (next, eslint-config-next), `react` (react, react-dom, `@types/react*`), `vitest` (vitest, `@vitest/*`), `production` and `development` (minor and patch), and `actions` for github-actions (minor and patch). Both ecosystems use label `dependencies` and commit prefix `chore`.

Vulnerability alerts and automated security fixes are already enabled by `scripts/setup-github.sh` and checked by `check-github.sh`. Dependabot ignores labels that don't exist, so the script also creates `dependencies`.

## Order of work

1. Commit this plan on `spec/M0.7-dependabot`.
2. Add `dependabot.yml`; validate it against SchemaStore's `dependabot-2.0` schema (no new dependency).
3. Update the setup script, workflow guard and docs.
4. Run lint, format check, tests and the boundary validator; open the PR (Closes #26).
5. After merge, the tech lead re-runs `scripts/setup-github.sh` and `check-github.sh`.

## Risks

- **Claude review on Dependabot PRs:** they get no Actions secrets, so `claude-code-review` would fail on each. The guard skips it there; CI still runs.
- **Codecov upload** skips for the same reason; it is already non-blocking.
- **Grouping precedence** may behave differently than expected: the first weekly run shows it; the fix is config-only.
