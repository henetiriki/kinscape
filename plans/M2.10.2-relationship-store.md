# Plan: M2.10.2: Relationship table and store

- **Spec:** #771
- **Requirement IDs:** [PPL-02](../docs/requirements.md#ppl-02), [NFR-09](../docs/requirements.md#nfr-09)
- **Status:** approved

## Approach

Migration `0005_relationships.sql` adds a `relationship` table from `server/db/TEMPLATE.sql`. Its columns follow the requirements' data model (M2.10.1 D1): `person_a_id`, `person_b_id`, `type`, `subtype`, six `start_` and six `end_` FuzzyDate columns. A parent row holds the parent in A and the child in B. A spouse row holds the marriage in `start_` and the divorce in `end_`. Two composite foreign keys reference `person (tree_id, id)`. Checks allow a subtype only on a parent and dates only on a spouse.

`TreeStore` gains `listRelationships`, `findRelationship`, `addRelationship` and `updateRelationship`, which work as the Person methods do (M2.8). `addRelationship` also checks that both Persons are in the Tree. If one is not, it returns `not-found` and saves nothing. Update writes only the subtype or the dates. `Relationship` gains `version`.

The #535 note: this slice checks both Persons and updates by Tree and id (D1). M2.10.3 (#772) wires these methods into the `relationships` group of `openTree`.

## Decisions

**D1 · An update that names other Persons or another type** · Decides: Tech lead

An update never changes the Persons. What does the store do with an update whose Persons or type differ from the saved Relationship?

- **A.** Refuse it with `not-found` and change nothing. The update matches the row by Tree, id, type and both Persons.
- **B.** Refuse it with a new error, `mismatch`, that M2.11 can show.
- **C.** Keep the saved Persons and write only the subtype or the dates. Refuse a change of type with `not-found`.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- An ancestor query for the cycle rule: `checkRelationship` takes every Relationship, and about 4,000 rows is small.
- Catch the foreign-key error (`23503`) in place of a select: the memory store needs the same check.
- One table for each type: the requirements give one Relationship row.

## Risks

- The diff is near the 600-line cap: about 280 lines of code and 300 of tests. If it passes the cap, the build stops ([too-big rule](README.md#too-big)).
- A spouse update with the two Persons swapped gives `not-found` (D1 A).
