# Plan: M2.11.3: Relationship actions: create and update

- **Spec:** #817
- **Requirement IDs:** [PPL-02](../docs/requirements.md#ppl-02), [NFR-09](../docs/requirements.md#nfr-09)
- **Status:** approved

## Approach

Two actions join `createPersonAction` in `app/people/actions.ts`, built on `treeAction`. They share its `revalidated` helper, so a save drops the cached pages under `/people`.

`relationshipInputSchema` refuses a divorce before the marriage with a Zod issue, so a plain parse gives `invalid`. A new `checkRelationshipInput` in `lib/domain/relationships/form.mts` follows `checkPerson`. It maps that one issue to `divorce-before-marriage` (D1 A of the Spec), and any other issue to `invalid`. Each action calls it before the group, so a bad input saves nothing.

`createRelationshipAction` then calls `tree.relationships.create`. `updateRelationshipAction` takes `{ relationship, version }` as `updatePersonAction` does, and calls `tree.relationships.update`. The group gives the four refusals, `tree-full`, `conflict` and `not-found`. The action returns each one as it is.

A new `RelationshipSaveError` type in `lib/domain/relationships/types.ts` lists every code. M2.11.4 (#826) maps each code to a message and wires the actions to its dialog.

Next.js posts an action to the URL of the page that calls it. M2.11.4 calls these from `/people/{id}/relationships`, so the `/people/:path*` rule in `next.config.ts` sets `private, no-store` on the response.

## Alternatives considered

- A spouse schema without the refine, and a separate date check: two places would define one rule.
- A new action file: it would copy `revalidated`.

## Risks

- The group runs the rules before the store (M2.10.3 D1 A). An update that changes the Persons and also breaks a rule gives the refusal, not `not-found`. A stale update that breaks a rule gives the refusal, not `conflict`. Only a hand-made request changes the Persons, and nothing saves in either case.
- This Spec has no page, so no e2e test can post an action. M2.11.4's e2e test checks `Cache-Control` on the action's response.
- The `tree-full` case seeds 10,000 rows through the memory store, as the contract test does.

## Deviations

- `schemas.mts` exports `DIVORCE_BEFORE_MARRIAGE`. A bad divorce date text also raises a `custom` issue at `divorce`, so `checkRelationshipInput` matches the message.
- The `Cache-Control` check on an action response moves to M2.11.4 (#826). No page calls the actions in this Spec, so no test can post one.
- I wrote `form.test.ts` and `form.mts` in one step, so I did not see the `form.test.ts` cases fail first.

## Out of scope

The page, the picker, the dialog and the messages (M2.11.4).
