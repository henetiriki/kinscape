# Plan: M2.11.4.1: Relationships page

- **Spec:** #826
- **Requirement IDs:** [PPL-02](../docs/requirements.md#ppl-02), [NFR-05](../docs/requirements.md#nfr-05)
- **Status:** approved

## Approach

The route `app/people/[id]/relationships/page.tsx` reads in two steps through `treeAction`. First it reads the Person, so a failed link read keeps the name (D6). Then it lists the Relationships, keeps the Person's, and reads each other Person by id. A pure function groups the links and sorts each group with `byName`. A client view, `PersonRelationships`, draws the board inside `EditOnComputer`. Three `/screens` routes give the boards synthetic data for `npm run design:check`.

## Risks

- A link whose other Person is gone: the store's foreign keys stop it. The page skips the row, because `persons.get` can return `undefined`.
- The server lists at most `MAX_RELATIONSHIPS` Relationships. It reads and sends only the linked Persons.

## Deviations

- `groups.mts` also exports `linkedPersonIds`, so the page reads only the linked Persons. `LinkedPerson` is in `relationships/types.ts`.
- `dates.mts` also holds `spouseDates`.
- `PersonRelationships` takes a union of props: `failed` has no `groups`.
- `features/people/index.ts` exports the two row types.
- The `private, no-store` check is a separate e2e test, not in the header loop.
- The `person-relationships` board lists parents and spouses unsorted. The page sorts them (D2). A person raises the Bug for the board.
