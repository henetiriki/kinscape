# Plan: M2.12.2: Place table and store

- **Spec:** #879
- **Requirement IDs:** [PIN-02](../docs/requirements.md#pin-02), [PIN-06](../docs/requirements.md#pin-06), [NFR-09](../docs/requirements.md#nfr-09)
- **Status:** approved

## Approach

Migration `0006_places.sql` adds a `place` table from `server/db/TEMPLATE.sql`. Its columns are `latitude` and `longitude` (`double precision`) and `precision` (`text`). A check allows only the nine `PLACE_PRECISIONS`, as `person` checks `sex`. No check limits the latitude or the longitude (Spec, Flagged concerns). A `double precision` column holds a JavaScript number exactly, so a read returns the Place that the add saved.

`Place` in `lib/domain/places/types.ts` is `{ version: number } & PlaceInput`, as `Relationship` is. `TreeStore` gains `listPlaces`, `findPlace`, `addPlace` and `updatePlace`. They work as the Relationship methods do (M2.10.2):

- `addPlace` and `updatePlace` return a `Result` with `not-found`, which the `places` group of M2.12.5 (#882) passes on.
- `updatePlace` replaces the latitude, the longitude and the precision. It returns `conflict` for a stale `version` (Spec D1).
- `listPlaces` returns at most `MAX_PLACES` Places, ordered by id (Spec D2, plan D3).

In the memory store, a `readOnly` Tree refuses the two new writes, and a `failing` Tree throws on `listPlaces`, as for the other groups. M2.12.5 (#882) wires the four methods into `openTree`.

## Decisions

**D3 · The number of Places in a list** · Decides: Tech lead

Spec D2 lets the plan set the cap. Person has `MAX_LISTED` (2,000) and Relationship has `MAX_RELATIONSHIPS` (10,000). M2.13.2 (#859) checks the map with 10,000 Pins. M2.13.5 (#863) checks 10,000 Pins on 500 Places. M2.14.2 (#865) D2: A makes a new Place for each new point, so a Tree can hold one Place for each Pin. M2.12.4 (#881) D2 lets its plan set the Pin cap, and no value is set yet.

- **A.** A new `MAX_PLACES` of 10,000 in `lib/domain/places/schemas.mts`. The cap test adds 10,001 Places, as the Relationship cap test adds 10,000 rows with a 120 s timeout.
- **B.** Reuse `MAX_LISTED` (2,000). The cap test is five times faster. A Tree with more than 2,000 Places loses the Places past the cap. Option B changes #859, whose 10,000 Pins can then name Places that the list does not return.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- `numeric` columns: `pg` returns a `numeric` as a string, so each read must convert it.
- `addPlace` returns `undefined` for a refusal, as `addPerson` does: M2.12.5 then maps it to `not-found`. A `Result` is the newer pattern (`addRelationship`).
- A check on the latitude and longitude range: the Spec flags it, and the tech lead decides whether to build it.

5. Run the checks in `AGENTS.md`.

## Risks

- The diff is about 650 lines, which passes the cap by about 50. The Spec says that the tech lead accepts it. If the diff passes 700 lines, the build stops ([too-big rule](README.md#too-big)).
- `precision` is a Postgres keyword. Postgres allows it as a column name, and Kysely quotes each name. If the migration fails on it, the build quotes it.
- No M2 action calls `updatePlace`. M2.14.2 (#865) and M2.15.1 (#540) D1 change nothing on a Place. The method follows Spec D1, and the `places` group of M2.12.5 wires it.
- If D3 is A, the cap test is as slow as the Relationship cap test. It gets the same 120 s timeout.

## Out of scope

As the Spec says: Pins (M2.12.3), the `places` group in `openTree` (M2.12.5), PlaceName and place search (M3), and delete. A seed Tree gets no Places in this Spec.

## Deviations

- The memory store shares one `rowsOf` helper for `relationshipsOf` and `placesOf` (a35c3f59). The database store keeps the copies of `addPlace` and `updatePlace`: a helper for them needs typed Kysely generics and edits Person code outside this Spec. The tech lead chose this.
