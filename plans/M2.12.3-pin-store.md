# Plan: M2.12.3: Pin table and store

- **Spec:** #880
- **Requirement IDs:** [PIN-02](../docs/requirements.md#pin-02), [PIN-03](../docs/requirements.md#pin-03), [PIN-06](../docs/requirements.md#pin-06), [NFR-09](../docs/requirements.md#nfr-09)
- **Status:** draft

## Approach

Migration `0007_pins.sql` adds a `pin` table from `server/db/TEMPLATE.sql`. It has these columns and rules:

- `person_id` and `place_id`, each with a composite foreign key to `person` and `place`. So a row never points into another Tree.
- `event_type`, with a check for the ten `EVENT_TYPES`, as `person` checks `sex`.
- `address`, `sources` and `notes` (`text not null default ''`). The schema of M2.12.1 checks their length, as for Person `notes`.
- The date as six `date_` columns with the FuzzyDate checks of `person`. Each is `not null`, except `date_date2`, because the date is required (#537 D2).
- An index on `(tree_id, date_valid_from, date_valid_to)`, because M2.12.4 (#881) queries Pins by day. The template asks for it, and a migration is never edited.

`Pin` in `lib/domain/pins/types.ts` is `{ version: number } & PinInput`, as `Place` is. `TreeStore` gains `findPin`, `addPin` and `updatePin`. They return a `Result` with `not-found` and `conflict`, as the Relationship methods do:

- `addPin` and `updatePin` give `not-found` if the Person or the Place is not in the Tree. The check runs before the write, so nothing saves.
- `updatePin` replaces every field, including the Person and the Place. It gives `conflict` for a stale `version` (Spec D1).

The memory store checks the Person and the Place with a `pinnable` helper, as `joinable` checks the Persons of a Relationship. The shared `added` and `updated` helpers of C1083 do the rest. The database `updated` helper gets an optional `check`, as `added` has. A `readOnly` Tree refuses the two new writes. There is no list, so `failing` does not apply. M2.12.5 (#882) wires the three methods into `openTree`.

## Alternatives considered

- The `placed_` prefix of the template: the field is `date`, and `person` names its columns after its fields (`birth_`).
- A write that catches the foreign key error: Postgres then logs an error for a normal refusal, and the memory store has no such error.
- `addPin` returns `undefined` for a refusal, as `addPerson` does: a `Result` is the newer pattern (`addPlace`, `addRelationship`).

## Order of work

1. Add `Pin` and the three `TreeStore` method types.
2. Write the Pin cases in the contract suite. See them fail on the behaviour, and record the failing line.
3. Write the migration and the table type. Then write the memory store, then the database store.
4. Add the `readOnly` case. Update the migrate and scoping tests.
5. Run the checks in `AGENTS.md`.

## Risks

- The diff is about 800 lines, which passes the cap by about 200. The Spec says that the tech lead accepts it. If the diff passes 850 lines, the build stops ([too-big rule](README.md#too-big)).
- The check and the write are two queries. No store method deletes a Person or a Place, so the check stays true. The foreign keys still refuse a row that points into another Tree.
- M2.12.4 (#881) clips each span by the Person's birth and death. The day index may not suit that query. M2.12.4 can then add an index in a new migration.

## Out of scope

As the Spec says: the span and the day query (M2.12.4), the `pins` group in `openTree` (M2.12.5), delete and source records (PIN-07). The one-step saves with a new Place are M2.14.2 (#865 D3) and M2.15.1 (#540 D2). A seed Tree gets no Pins.
