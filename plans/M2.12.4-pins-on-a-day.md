# Plan: M2.12.4: Pins on a day and the Pin list

- **Spec:** #881
- **Requirement IDs:** [PIN-04](../docs/requirements.md#pin-04), [PIN-06](../docs/requirements.md#pin-06), [NFR-09](../docs/requirements.md#nfr-09)
- **Status:** approved

## Approach

A pure function `spanOf` in `lib/domain/pins/span.mts` gives the span of a Pin. It takes the Pin's date and the birth and death of its Person:

- The start is the later of the date's `validFrom` and the birth's `validFrom` (the earliest day of the birth).
- The end is the earlier of the date's `validTo` and the death's `validTo` (the latest day of the death, plus one).
- A missing birth or death clips nothing. The rule is the same for each qualifier (Spec D1).
- If the start is after the end, the end becomes the start. So an empty span is never reversed, and `isCurrentOn` is false on each day.

`TreeStore` gains two reads. Each is empty if the Account may not access the Tree, as `listPlaces` is:

- `listPins(scope)` gives at most `MAX_PINS` Pins of the Tree, ordered by id, each as a `SpannedPin` (`{ span: Validity } & Pin`).
- `listPinsOn({ day, ...scope })` gives at most `MAX_PINS` Pins whose span holds `day` under `isCurrentOn`, ordered by id.

The memory store reads the Person of each Pin from its own map, calls `spanOf`, then filters, sorts and caps. `listPins` joins the `failing` list reads.

The database store joins `pin` to `person` on `(tree_id, person_id)`. `listPins` maps the Person's date columns to `spanOf`. `listPinsOn` clips in SQL, so `limit` caps the right rows:

- `greatest(pin.date_valid_from, person.birth_valid_from) <= day`;
- `day < least(pin.date_valid_to, person.death_valid_to)`.

Postgres `greatest` and `least` skip a null, so a missing birth or death clips nothing, as in `spanOf`. The query also keeps `date_valid_from <= day < date_valid_to`, so it can use `pin_date_idx`. Both reads use the Person as saved when they run, so a later death changes the result.

M2.12.5 (#882) wires the two reads into the `pins` group (Spec D3).

## Decisions

**D1 · The value of `MAX_PINS`** · Decides: Tech lead

Spec D2 lets the plan set the cap. `docs/requirements.md` sizes a Tree at 10,000 Pins, and `MAX_PLACES` and `MAX_RELATIONSHIPS` are 10,000. #859 D1 seeds 10,000 synthetic Pins into the one CI Tree, and the `@perf` checks of #859 and #863 time 10,000 Pins.

- **A.** 10,000. The CI Tree of #859 then sits at the cap. A Pin that another e2e test adds there can sort after the seed and drop out. #859's plan then seeds Pin ids that sort last, or fewer Pins (one line). Changes #859.
- **B.** 20,000. The CI Tree keeps room. The cap test seeds 20,001 Pins on PGlite, about twice the time of A. The largest response is twice the size, and no `@perf` check times it.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- The day query filters the output of `listPins` by day: a Tree with more Pins than the cap then loses current Pins that sort past it.
- The database day query reads each Pin of the Tree and filters with `spanOf`: it reads up to the whole Tree for each day. The contract check "day in span if and only if returned" holds the SQL and `spanOf` to one rule.
- A span column on `pin`: a change to a birth or a death must then rewrite each Pin of that Person (Spec: the query uses the Person as saved).

## Risks

- The cap case adds 10,001 Pins through the store on PGlite, about five queries each. One case proves both caps. If it passes the 120 s timeout of the Places cap case, the build raises the timeout and writes a Deviation line.
- `listPinsOn` takes a `Day`. Postgres throws for a day that is not an integer, and memory finds nothing. No caller in this Spec takes a day from a client. M2.12.5 and the route validate it. A fix is an `isDay` check, as `isVersion` is (small).
- The SQL and `spanOf` state the clip twice. The "if and only if" case runs on both adapters and fails if they differ.
- The join drops no Pin: the foreign key keeps each Person, and no store method deletes one.
