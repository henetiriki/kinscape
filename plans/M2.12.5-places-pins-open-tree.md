# Plan: M2.12.5: Places and Pins in openTree

- **Spec:** #882
- **Requirement IDs:** [PIN-06](../docs/requirements.md#pin-06), [NFR-09](../docs/requirements.md#nfr-09), [NFR-10](../docs/requirements.md#nfr-10)
- **Status:** approved

## Approach

`openTree` gains a `places` group and a `pins` group beside `relationships`. Each group follows `personGroup`. It takes the store, the Viewer and the Tree id of the opened Tree, and it calls the store methods of M2.12.2 to M2.12.4 with that scope.

Two new views in `server/trees/views.mts` hide nothing in v1 (NFR-10). `placeView` maps a `Place`. `pinView` maps a `Pin`. The `list` of the `pins` group passes each `SpannedPin` through `pinView` and then adds the span again. Thus one view decides what a Viewer sees of a Pin, and the Spec's flagged address rule can go there later.

A write returns the store result. On success, the group passes the saved row through its view. The groups add no rule and no extra read, so the store gives `not-found` and `conflict`.

## Decisions

**D1 · The name of the day query in the `pins` group** · Decides: Tech lead

The store has `listPins` and `listPinsOn`. #538 calls `pins.list`, and #861 calls `pins.get`. No related issue names the day query.

- **A.** `listOn(day: Day)`. It matches the store name `listPinsOn`.
- **B.** `on(day: Day)`. It is shorter.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- A second view for `SpannedPin`: two views would decide what a Viewer sees of one Pin.
- A generic `pinView`: `ToView<Row, View>` takes no type parameter, so the type would change for one caller.

## Order of work

1. Add the types and the two views.
2. Write the contract cases. See them fail on the missing groups, not on an import error.
3. Add `placeGroup` and `pinGroup`, and wire them into `openTree`.
4. Run the checks in `AGENTS.md`.

## Risks

- A later view that hides a field must keep `span` on the list. The list case checks the span, so a change that drops it fails.
- The list and the day query return at most `MAX_PINS` (10,000), as M2.12.4 sets. The groups add no paging.
