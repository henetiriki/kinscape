# Plan: M2.13.6: Pin details route

- **Spec:** #861
- **Requirement IDs:** [PIN-02](../docs/requirements.md#pin-02), [NFR-03](../docs/requirements.md#nfr-03), [NFR-10](../docs/requirements.md#nfr-10)
- **Status:** approved

## Approach

**Dates on the map.** `MapPin` (`lib/domain/pins/types.ts`) gets `Pick<FuzzyDate, 'date1' | 'date2' | 'qualifier'>`. `mapPins` copies the three fields from `pin.date`. It copies no `earliest`, `latest` or `precision`. `mapPins` reads only the Pins that `pins.list` returns, and `pins.list` maps each row through `pinView`. A Pin that a Viewer may not see never reaches `mapPins`, so its dates never leave the server (NFR-10). #862 builds both date lines with `fuzzyDateOf(qualifier, date1, date2)`, `readFuzzyDate` and `formatFuzzyDate`.

**The details.** A new type `PinDetails` holds `address`, `eventType`, `givenNames` and `surname`. A pure function `pinDetails(pin, person)` in `lib/domain/pins/pin-details.mts` builds it. It holds no date, source, note, precision, id or `version` (#861 D3).

**The route.** A new route handler, `app/data/pins/[id]/route.ts`, answers `GET`, as `app/data/pins/route.ts` does:

1. It calls `currentSession()`. With no session it answers 401 with no body.
2. It reads through `treeAction(z.string(), …)`, as `app/people/[id]/page.tsx` does. The body calls `parsePinId` before any read. An id that is no UUID gives `ok(undefined)`.
3. The body calls `pins.get`, then `persons.get(pin.personId)`. A missing Pin or Person gives `ok(undefined)`. `openTree` scopes both reads to the Viewer's Tree, so a Pin of another Tree reads as missing.
4. `ok(undefined)` answers 404 with no body (D4). A session with no Tree answers 401 with no body (#538 plan D3).
5. The details go out through `privateJson()`. A throw logs the error name only and answers 500 with no body.

The URL holds the Pin id only. The `[id]` folder is on the `ADDRESS_FOLDERS` list.

**The query.** `features/pins/query.ts` gets `fetchPinDetails(id)` and `usePinDetails(id)`. They stay in that file, because `QUERY_FILES` in `scripts/safety.mts` lists it. `usePinDetails` calls `useQuery` with the key `['pins', id]` (D6) and `staleTime: Infinity`. TanStack Query then holds the answer while the popup stays open, and for its default `gcTime` of 5 minutes after it closes. A second ask in that time sends no request. A 404 skips the retry (`app/query-retry.ts`). `features/pins/index.ts` exports `usePinDetails`. M2.13.4 (#862) wires it to the popup.

## Decisions

**D4 · The answer for an unknown Pin** · Decides: Tech lead

The Spec gives one answer to an id that is no UUID, names no Pin or names a Pin of another Tree. It does not name the status. #538 plan D3 answers 401 to a session with no Tree. #884 needs the same answer for `/data/pins/{id}/edit`. #862 shows its failed state on any failure.

- **A.** 404 with no body. A 401 then means only "signed out", and the browser can tell a lost session from a lost Pin. `retryQuery` skips both. #884 copies 404.
- **B.** 401 with no body, the same answer as signed out. The browser handles one refusal. #884 copies 401.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D5 · A Pin with one date** · Decides: Tech lead

The third acceptance check lists `date2` among the keys of each Pin. `FuzzyDate` holds `date2` only for `BET` and `FROM`, and `fuzzyDateOf` takes it as optional. #862 builds both date lines from these three fields.

- **A.** A Pin with one date has no `date2` key, as `FuzzyDate` does. The exact-keys tests check a range Pin with `date2` and a single-date Pin without it. No new type.
- **B.** Each Pin has a `date2` key, `null` for one date. `MapPin` then has a second date shape, and #862 maps `null` to `undefined`. About 5 lines.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D6 · The key of the details query** · Decides: Tech lead

M2.14.3 (#866), M2.14.6 (#869) and M2.15.2 (#884) load the Pins query again after a save, with the key `['pins']` (#538 plan, Risks). An edit can change the Person or the address of a Pin.

- **A.** `['pins', id]`. TanStack Query matches a key by its start, so a reload of `['pins']` also marks each held details query as stale. The popup then shows the edited Pin. #884 adds no code for it.
- **B.** `['pin', id]`. A reload of `['pins']` leaves the details as they were. #884 also reloads `['pin', id]`, about 3 lines.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- **The details on `MapPin`.** It sends each Person's name and address with the map (#678 D2).
- **A new query file.** `QUERY_FILES` would need a second entry for the same feature.
- **The route calls `openTree` directly.** The scoping rule lets `app/` reach `appAdapters` only through `treeAction`.

## Risks

- **Payload size.** The dates add about 50 bytes for each Pin. At 10,000 Pins the body of `/data/pins` grows from about 1.3 MB to about 1.8 MB before compression.
- **Two reads for each details request.** The route reads the Pin, then its Person. The foreign key of the `pins` table makes a missing Person unlikely. The route answers 404 for it, and a test covers the branch.
- **A held answer can go stale.** Another window can edit the Pin while this window holds its details. One user makes this unlikely. D6 (A) covers an edit in the same window.
