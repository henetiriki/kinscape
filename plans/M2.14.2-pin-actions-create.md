# Plan: M2.14.2: Pin actions: create

- **Spec:** #865
- **Requirement IDs:** [PIN-01](../docs/requirements.md#pin-01), [PIN-02](../docs/requirements.md#pin-02), [PIN-04](../docs/requirements.md#pin-04), [NFR-03](../docs/requirements.md#nfr-03), [NFR-10](../docs/requirements.md#nfr-10)
- **Status:** approved

## Approach

`app/@map/actions.ts` (`'use server'`) holds `createPinAction`. The map page is its only caller (M2.14.3, #866, M2.14.6, #869). The action runs through `treeAction` with `z.unknown()`, as `createPersonAction` does. The body then calls `checkPin`. This is the input:

```ts
{ id, personId, eventType, date, address?, sources?, notes?,
  place: { kind: 'new', id, latitude, longitude, precision? } | { kind: 'existing', id } }
```

`checkPin` (`lib/domain/pins/form.mts`) parses with `pinFormSchema` (`lib/domain/pins/schemas.mts`). The schema reuses the fields of `pinInputSchema` and `placeInputSchema`, so the caps and lists stay in one place. A missing precision gives `approximate`, as `placeInputSchema` does (#867). `checkPin` returns `{ pin: PinInput; place?: PlaceInput }`, with `pin.placeId` set from the Place id. Otherwise it returns `{ fields }`. Each field gets one of these kinds:

- `personId`, `eventType`, `date`, `place`, `latitude`, `longitude`: `required` if missing or blank.
- `eventType`, `precision`: `unknown`, outside its list.
- `date`: the `FuzzyDateError` of `parseFuzzyDate`.
- `latitude`, `longitude`: `not-a-number` or `out-of-range`.
- `address`, `sources`, `notes`: `too-long`.

Any other bad input gives `invalid` (D2). An error holds kinds only, never input text.

The store gets `addPinAt({ pin, place, ...scope })`. It saves a new Place and its Pin, or neither, and gives `Result<Pin, 'not-found'>`:

- **Database:** `db.transaction().execute(trx => …)` runs `databaseStore(trx).addPlace` and then `.addPin`. If `addPin` gives `not-found`, a private error rolls back the Place. The method catches that error and returns `not-found`.
- **Memory:** it runs `addPlace`, then `addPin`. If `addPin` fails and the Place id was not saved before the call, it deletes the Place.

`pins.createAt(pin, place)` calls `addPinAt` and returns the Pin through `pinView` (#865 D5). The action calls `tree.pins.createAt` for a new point and `tree.pins.create` for an existing Place. A repeat of the same ids changes nothing: each insert skips a saved id, and the action returns the Pin saved first (#865 D4).

The action calls no `revalidatePath`. The map reads Pins through the Pins query, and M2.14.3 loads that query again after a save.

## Decisions

**D1 · Where `Cache-Control: private, no-store` comes from** · Decides: Tech lead

A server action cannot set a response header. It answers on the route of the page that calls it. `next.config.ts` has a `private, no-store` rule for `/people/:path*` only. M2.14.3 (#866) has no check for the header.

- **A.** M2.14.3 (#866) adds the rule for `/`. `noStoreBreaks` (`scripts/__tests__/no-store.test.ts`) fails when `app/@map/page.tsx` imports the action, until the rule is there. The build rewords #866 to add an acceptance check for the header. This plan adds nothing to `next.config.ts`.
- **B.** This plan adds the rule for `/` to `next.config.ts` now. Cost: one rule that no fitness test asks for until #866 merges.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D2 · An input that the form already stops** · Decides: Tech lead

The Spec names an error for each field in its Check list. The form of M2.14.3 makes the ids and sends numbers. Only a client that is not the form sends a malformed id, an unknown key, a wrong `kind` or a NUL character.

- **A.** Each of these gives `invalid` for the whole input, as #814 plan D1 does. Nothing is saved.
- **B.** Each gives an error for its own field. The form of #866 needs a message for each.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D3 · The new point of M2.15.1 (#540)** · Decides: Tech lead

#540 says the check of this Spec checks its update "with the same rules". Its new point has a latitude, a longitude and a precision, with no Place id. This plan's new point carries a Place id that the client makes (#865 D4).

- **A.** #540 reuses the new-point schema of `pinFormSchema`, with the Place id. A repeat of an update then saves no second Place. The build rewords the Input of #540.
- **B.** #540 keeps a new point with no id. Its plan builds a second new-point schema, and the server makes the Place id. Cost: a repeat of the update can save a second Place.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- `app/pins/actions.ts`: no page lives there, and the map page in `app/@map/` is the only caller.
- Tell a new point from an existing Place by its keys, with no `kind`. A point with only a latitude would then be an existing Place with an unknown key, and give `invalid`, not a `longitude` error.
- One SQL statement for both inserts. Two calls of the existing `addPlace` and `addPin` keep one insert for each kind.

## Risks

- **A retry with a new Place id.** If a client sends a saved Pin id with a new Place id, `addPinAt` saves the Place and returns the saved Pin. The Place then holds no Pin. Likelihood: low, if the form of #866 makes both ids once for each panel. Fix: `addPinAt` reads the Pin first and returns it before it saves the Place. Cost: about 10 lines and one contract case.
- **A thrown store error.** In production, Next replaces the message of a thrown action error with a digest. The action logs nothing.
- **Export shape.** Each export of a `'use server'` file must be an async function. `treeAction` returns one, and `npm run build` checks it.
- **Size.** The Spec estimates about 650 lines. If the diff passes that by much, the build stops as the [too-big rule](README.md#too-big) says.

## Deviations

- `memory-store.mts` moves `addPin` and `addPlace` out of the returned object, so `addPinAt` can call them.
- `database-store.test.ts` gains one case: `addPinAt` throws a database error and does not turn it into `not-found`.
- `addPinAt` joins the Pin to `place.id` and ignores `pin.placeId`. `checkPin` sets both to the same id.
- `lib/domain/forms/field-errors.mts`, its test and `lib/domain/forms/types.ts` are new. They hold `collectFieldErrors`, which maps zod issues to field errors. A review finding asked for one shared helper.
- `lib/domain/persons/form.mts` changed. `checkPerson` now calls `collectFieldErrors`, and its behaviour is the same.
- The CI agent did not execute `npm run build`. It cannot set `KINSCAPE_MEMORY_ADAPTERS=1` (the CI agent rules deny a `VAR=` prefix), and nothing imports `createPinAction` yet.
