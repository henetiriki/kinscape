# Plan: M2.14.3.3: Persons route and query

- **Spec:** #1126
- **Requirement IDs:** [PIN-01](../docs/requirements.md#pin-01), [NFR-03](../docs/requirements.md#nfr-03), [NFR-10](../docs/requirements.md#nfr-10)
- **Status:** draft

## Approach

**The route.** A new route handler, `app/data/people/route.ts`, answers `GET`, as `app/data/pins/route.ts` does:

1. It calls `currentSession()`. With no session it answers 401 with no body.
2. It reads through `treeAction(z.undefined(), …)`. The body maps `tree.persons.list()` through `personSummary`, as `app/people/(list)/page.tsx` does. `PersonSummary` has no notes.
3. `answerOf` (`app/data/tree-route.ts`) sends the rows through `privateJson()`. A session with no Tree gives a failed Result, and `answerOf` answers 401 with no body. An empty list is not `undefined`, so a Tree with no Person gets `[]`.
4. `guarded('People route', …)` answers 500 with no body for a throw, and logs the error name only.

`persons.list` returns at most `MAX_LISTED` (2,000) Persons (`lib/domain/persons/schemas.mts`), so the answer has a cap ([scale rule](../docs/code-rules.md#scale)).

**The query.** A new file `features/people/query.ts` holds `fetchPeople` and `usePeople`, as `features/pins/query.ts` holds `fetchPins` and `usePins`. `fetchPeople` asks `/data/people`. A response that is not OK throws an error with its `status`, so `retryQuery` skips a 401. `usePeople` calls `useQuery` with the key `['people']` and `gcTime: 0`. TanStack Query then removes the Persons when the last reader unmounts, and the next reader asks again (D1). `features/people/index.ts` exports `usePeople`. M2.14.3.4 (#1123) and M2.15.2 (#884) wire it.

**The checks.** `QUERY_FILES` in `scripts/safety.mts` gets `features/people/query.ts`. `fetchBreaks` and `treeUrlBreaks` then pass for it. The route uses `privateJson()`, so `jsonRouteBreaks` passes.

## Decisions

**D1 · When the query asks again during one open** · Decides: Tech lead

The Spec asks again at each open of a form. It does not say what happens while the form stays open. #1123 asks "at each open of the panel, and not before" (its D6 B). #884 asks again only for a request that failed ("Try again", its D3 A). `usePins` uses `staleTime: Infinity`.

- **A.** `gcTime: 0` and `staleTime: Infinity`. The query asks once for each open. A window focus or a second reader in the same open sends no request. "Try again" calls `refetch`, which asks in both options.
- **B.** `gcTime: 0` and the default `staleTime` of 0. The query also asks again at each window focus, at each reconnect and when a second reader mounts. A Person that another tab adds then shows in the open form. Cost: more requests that send each Person again.
- **Other:** your own.

Recommended: A, because #1123 and #884 load the Persons at the open only.

**D2 · The error of a failed request** · Decides: Tech lead

`features/pins/query.ts` holds `requestError(status)`. The layer rules do not let `features/people` import from `features/pins`. The [code rules](../docs/code-rules.md#code-smells-not-style) forbid a copied helper.

- **A.** Move `requestError` to a new file `lib/domain/requests/request-error.mts`. It takes a label, such as "Pins" or "People", and the status. Both query files import it. Cost: about 25 lines, and `features/pins/query.ts` changes.
- **B.** Copy the helper into `features/people/query.ts`. Cost: two copies of the same rule, against the code rules.
- **Other:** your own.

Recommended: A, because the retry rule reads `status` from both queries, and one helper keeps them the same.

## Alternatives considered

- **The Persons in the map page.** `app/@map/page.tsx` reads them on each load of `/`. #1123 D6 chose the route.
- **A query in `features/pins`.** The Persons belong to the `people` feature, and the Spec names `features/people/query.ts`.

## Risks

- **No caller on `main`.** Nothing mounts `usePeople` until #1123 merges. The wiring rule allows it, because this plan names #1123 and #884.
- **Payload size.** A `PersonSummary` is about 250 bytes. At 2,000 Persons the body is about 500 KB before compression. The Spec flags a Tree of many thousand Persons for a later search route.
- **The cap hides Persons.** A Tree with more than 2,000 Persons sends only the first 2,000 by name. The form then cannot pick the others. One family's Tree makes this unlikely in v1. A fix is the search route that the Spec puts out of scope.
