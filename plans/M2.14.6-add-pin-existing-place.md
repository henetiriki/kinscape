# Plan: M2.14.6: "Add a pin here" on an existing Place

- **Spec:** #869
- **Requirement IDs:** [PIN-01](../docs/requirements.md#pin-01), [PIN-06](../docs/requirements.md#pin-06), [NFR-05](../docs/requirements.md#nfr-05)
- **Status:** draft

## Approach

The tech lead builds this plan in a local session (Spec D4). The session first sets the `form-existing-place` coordinates of `Map-add-pin.dc.html` to "-29.120000, 26.210000" (Spec D3).

`MapPin` gets `placeId`, and `PinDetails` gets the `precision` of the Pin's Place (Spec D1). The details route reads the Place with `tree.places.get`. A missing Place reads as none, as a missing Person does.

`PinForm` takes an optional `place` (`Pick<Place, 'id' | 'latitude' | 'longitude' | 'precision'>`). With a `place`, these things happen:

- The coordinates field is disabled. It shows `pointText` of the Place and the helper "This Place is fixed. You cannot change its point."
- The precision field is disabled. It shows the Place's precision with the board's note "This is the precision of the Place."
- Save sends `place: { kind: 'existing', id }`. The form parses no coordinates, because a disabled field sends no form value.

`useAddPin` returns `addHere(place)`. It opens the panel at the Place with a new key, so a second "Add a pin here" clears the typed values. `onEmptyClick` leaves a panel at a Place unchanged and opens no popup (Spec D2).

`PinPopup` gets an optional `onAddHere` for its button. `MapWithPins` calls `add.addHere` with the Place from the `MapPin` and the details, then closes the popup.

`PinPopup` is in `CONTROLS`, so its new prop changes a design system input (plan D1).

## Decisions

**D1 · The design system done checks** · Decides: Tech lead

The new `onAddHere` prop of `PinPopup` changes a design system input (`design/CANVAS.md` › When). That section's _Issue text_ gives such a Spec two done checks. #869 has neither. #868 changed `ClickPopup` in the same way, and its Spec had neither.

- **A.** The build adds the two done checks to the Acceptance checks of #869 (reword step). The local session runs steps 2 to 6 after the code. Cost: two more checks, and one more publish in the same session.
- **B.** The build runs steps 2 to 6, and the Spec stays as it is, as #868 did. Cost: the Spec does not show the design system change.
- **Other:** your own.

Recommended: A, because `design/CANVAS.md` says such a Spec has the two checks. B loses only the record in the Spec.

## Alternatives considered

- A query param on `/screens/pin-form` for the dev page. No dev screen reads search params, and `map-pin-popup` already uses a subroute for a state.
- A sample Place in `lib/design/samples.mts`. That file is a design system input. The sample stays in the screen file.
- An e2e test that first saves its own Pin. That adds two Pins to the seeded Tree, and the seed leaves room for five.
