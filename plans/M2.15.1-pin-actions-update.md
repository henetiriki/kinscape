# Plan: M2.15.1: Pin actions: update

- **Spec:** #540
- **Requirement IDs:** [PIN-02](../docs/requirements.md#pin-02), [PIN-04](../docs/requirements.md#pin-04), [NFR-03](../docs/requirements.md#nfr-03), [NFR-10](../docs/requirements.md#nfr-10)
- **Status:** approved

## Approach

`app/@map/actions.ts` gets `updatePinAction`, beside `createPinAction`. It runs through `treeAction` with `z.unknown()`, and the body calls `checkPinUpdate`. This is the input:

```ts
{ id, version, personId, eventType, date, address?, sources?, notes?,
  place: { kind: 'stays' } | { kind: 'new', id, latitude, longitude, precision? } }
```

`pinUpdateSchema` (`lib/domain/pins/schemas.mts`) is `pinFormSchema` with `version` and the other `place` union. `version` is `z.number().int().positive()`, as in `updatePersonAction`. The `new` member is the new-point schema that `pinFormSchema` uses now. The build moves it to its own constant, `newPointSchema`, so both unions use one copy (#865 plan D3).

`checkPinUpdate` (`lib/domain/pins/form.mts`) parses with `pinUpdateSchema` and maps each issue with `pinFieldError`, the field table of `checkPin`. A bad `version`, an unknown key or a wrong `kind` gives `invalid` for the whole input, as #865 plan D2 does. It returns `CheckedPinUpdate`: `{ pin, place?, version }`, with `pin` as a `PinInput` with no `placeId`.

The action then does one of these:

- **Place stays:** it reads the Pin with `tree.pins.get`. A missing Pin gives `not-found`. Otherwise it calls `tree.pins.update` with the saved `placeId` (#540 D4). The Place does not change (#540 D1).
- **New point:** it calls `tree.pins.updateAt(pin, place, version)`.

The store gets `updatePinAt({ pin, place, version, ...scope })`. It saves a new Place and the update, or neither, and gives `Result<Pin, 'conflict' | 'not-found'>`. The Pin joins `place.id`, whatever `pin.placeId` says, as in `addPinAt`. Both adapters share one helper with `addPinAt`:

- **Database:** `PinRefused` carries the error of the refused write. The helper runs `addPlace` and the Pin write in `db.transaction()`. If the write fails, it throws `PinRefused`, which rolls back the Place. It then catches the error and returns its result.
- **Memory:** the helper runs `addPlace`, then the Pin write. If the write fails and the Place id was not saved before the call, it deletes the Place.

A repeat of an update that saved has a stale `version`. `updatePin` gives `conflict`, and the transaction rolls back. The Place of the first update was saved before the call, so it stays, and no second Place is saved.

`pins.updateAt` calls `updatePinAt` and returns the Pin through `pinView`. A Place id of another Tree names no saved Place in the Account's Tree, so `addPlace` saves a new Place there (#540 D5).

The action calls no `revalidatePath`. M2.15.2 (#884) loads the Pins query again after a save. The action answers on the route of the map page. M2.14.3 (#866) adds the `private, no-store` rule for `/` to `next.config.ts` (#865 plan D1), and #884 is blocked by #866.

## Decisions

**D1 · Where `checkPinUpdate` and its schema sit** · Decides: Tech lead

The Check line of #540 says that this Spec exports the new-point schema and the field table from `lib/domain/pins/`. On `main`, `formPlaceSchema` sits in `schemas.mts` and `pinFieldError` sits in `form.mts`. Each update part fits in the file of its create part.

- **A.** `pinUpdateSchema` goes in `schemas.mts`, and `checkPinUpdate` goes in `form.mts`. The new-point schema and the field table stay unexported, because each has its users in its own file. The build rewords the Check line of #540 to "shares". Cost: none.
- **B.** As #540 says: export `newPointSchema` and `pinFieldError`. Put `pinUpdateSchema` and `checkPinUpdate` in a new file, `lib/domain/pins/update.mts`. Cost: one more file and two exports.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D2 · A new point with the id of a Place in the Account's own Tree** · Decides: Tech lead

#540 flags this case for the tech lead. `addPlace` returns the Place saved first, so the Pin joins that Place, with its old point. `createPinAction` (#865) has the same result for the same input. Only a hand-made request sends such an id, and the data stays in the Account's own Tree.

- **A.** Build no fix. The case stays under Risks. Cost: none.
- **B.** `updatePinAt` gives `not-found` for a new-point id that names a saved Place. It must read the Pin's `version` first, so a repeat still gives `conflict` (#540 acceptance check). `createPinAction` keeps its result. Cost: about 30 lines and three contract cases.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- A second `checkPin` mode for "stays": #540 D3 B, not chosen.
- `version` outside the Pin, as `updatePersonAction` takes it. #540 puts `version` in the update schema, so one parse checks every field.
- Update the Pin before the Place is saved. The composite foreign key of `pin` to `place` refuses a Place id that is not yet saved.

5. Run the checks in `AGENTS.md`.

## Risks

- **A new point with an own Place id** (D2 A): the Pin joins that Place and keeps its old point. Likelihood: low, because the client makes the id as a UUID. Fix: D2 B.
- **Two windows edit one Pin:** the second save gives `conflict`, and a retry fails again (#540 Flagged concerns). Likelihood: low, with one user. Fix: a conflict board and message, after M2.15.2.
- **A Pin that moves between the read and the write:** "Place stays" reads the `placeId`, and another save can move the Pin first. The other save raises the `version`, so the update gives `conflict` and saves nothing.
- **Size:** #540 estimates about 500 lines. This plan counts about 600, with the helpers. If the diff passes that by much, the build stops as the [too-big rule](README.md#too-big) says.

- `checkPinUpdate` builds `place` from `id`, `latitude`, `longitude` and `precision`, and `pin` has no `placeId` in both place kinds.
