# Plan: M2.15.2: Edit a pin form

- **Spec:** #884
- **Requirement IDs:** [PIN-01](../docs/requirements.md#pin-01), [PIN-02](../docs/requirements.md#pin-02), [NFR-05](../docs/requirements.md#nfr-05)
- **Status:** draft

## Approach

A new route `/data/pins/{id}/edit` answers with `PinEditFields` (Spec D1). The route mirrors `/data/pins/{id}`: `guarded`, `treeAction`, `answerOf`. A missing Pin or Place reads as none, so each gets 404. `pinEditFields(pin, place)` in `lib/domain` copies only the fields of the Spec. It writes the date with `formatFuzzyDate`. `usePinEdit(id)` in `features/pins` asks for it, with the key `['pins', id, 'edit']` and `gcTime: 0`, so each "Edit" asks again.

`PinForm` gets an optional `edit` prop: the Pin id and the state of `usePinEdit`. With `edit`, these things happen:

- The title is "Edit a pin".
- The loading look shows until the Persons and the fields arrive (Spec D3).
- A failed load shows the title of Spec D8. "Try again" calls `refetch` on each failed query.
- The fields start with the Pin's values. The coordinates show `pointText` of the Place (Spec D10).
- While `parseCoordinates` of the text equals the Place's point, the precision is fixed with its note, and Save sends `place: { kind: 'stays' }`. Any other text frees the precision, and Save sends a new point.
- `checkFields` uses `checkPinUpdate` and adds the `version`.

`useAddPin` gets a flow kind `edit`, with the Pin id and a new key for each "Edit" (Spec D6). `edit(id)` replaces any flow. `addHere` replaces an edit flow. `onEmptyClick` leaves an edit flow alone (Spec D7). The button hides while either form is open. The edit save calls `updatePinAction`, then `onEdited`. `MapWithPins` passes `onEdited`, which calls `invalidateQueries({ queryKey: ['pins'] })`.

`PinPopup` gets an optional `onEdit` for its "Edit" button. `MapWithPins` calls `add.edit(pin.id)` and closes the popup (plan D2). `PinPopup` is in `CONTROLS`, so the build runs the design system steps (Spec D9).

## Decisions

**D1 · Where the edit boards get their Pin** · Decides: Tech lead

The boards show a Pin of Maria Magdalena du Toit at -29.12, 26.21. The fixture Trees of `server/auth/fixtures.mts` hold Persons and no Pins. Each design state runs after the page loads, so it cannot catch the first request.

- **A.** A dev page `/screens/pin-form/edit` opens the edit panel on mount for a synthetic Pin id. Each state routes `**/data/pins/*/edit` and then reloads the page. `pin-edit` and `pin-edit-moved` get a synthetic answer with Maria's fixture id. `pin-edit-loading` holds the request. `pin-edit-load-failed` gets 404. The Persons come from the real `/data/people`. Cost: about 50 lines, and the design check reads no real Pin.
- **B.** The Family Tree fixture gets a Place and a Pin. Loading and failed still need A's route. Cost: a new fixture shape, and each map test of `r.family@example.com` sees one more Pin.
- **Other:** your own.

Recommended: A, because the fixtures stay as they are and each state sets its own answer.

**D2 · The popup after "Edit"** · Decides: Tech lead

"Add a pin here" closes the popup (#869). The Spec does not say what "Edit" does to the popup.

- **A.** "Edit" opens the panel and closes the popup, as "Add a pin here" does. Cost: none.
- **B.** The popup stays open. Cost: after a move, it points at the old point until the Pins reload.
- **Other:** your own.

Recommended: A, because one Pin then shows in one place, the panel.

## Alternatives considered

- A separate `EditPinForm`. It would copy the fields, checks and Esc rule of `PinForm`.
- `usePinEdit` in `features/people`. A feature may not import another, and the key belongs with the Pins queries.

## Risks

- Size: about 1,250 lines, over the cap of 660. The tech lead keeps one Spec (Spec D5). The PR needs the `size: accepted` label.
- `pin-edit` fails `design:check` until step 7 redraws its coordinates. The build keeps the PR a draft until then.
- The e2e spec adds a Pin to the seeded Tree. `ALL` then allows four more, and the seed leaves room for five.
- A disabled field sends no form value. A test saves an unchanged point and checks that the input holds `kind: 'stays'` and no precision.
