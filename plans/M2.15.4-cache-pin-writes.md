# Plan: M2.15.4: Cache Pin writes with setQueryData

- **Spec:** #1130
- **Requirement IDs:** [PIN-01](../docs/requirements.md#pin-01), [PIN-02](../docs/requirements.md#pin-02), [NFR-03](../docs/requirements.md#nfr-03)
- **Status:** approved

## Approach

`createPinAction` and `updatePinAction` answer with the saved Pin as a `MapPin` (Spec D1 A). After the save, the action reads the Person and the Place of the Pin by id. It builds the entry with `spanOf` and `mapPins`, the two functions that `/data/pins` uses, so the answer and the list cannot differ (plan D2).

A new hook `useWritePin()` in `features/pins/query.ts` keeps all knowledge of the `['pins']` key in one file. It gives a function of one `MapPin`. The function calls `setQueryData<MapPin[]>(['pins'], pins => pins && withMapPin(pins, pin))`. An updater that returns `undefined` writes nothing, so a list that has not loaded stays empty. Then the function calls `invalidateQueries({ predicate, queryKey: ['pins'] })`, with the predicate that `main` uses now (plan D1).

`useSave` in `useAddPin` is the one save hook of the Spec. The add flow and the edit flow both use it. On an ok answer it calls the write function with `result.value`. `useAddPin` drops its `onSaved` and `onEdited` props, and `MapWithPins` drops its `refetch()` and `invalidateQueries` calls. A save that ends after Cancel or Esc still writes, because `useSave` does not depend on the open panel.

`withMapPin(pins, pin)` in `lib/domain/pins/map-pins.mts` gives a new list. The list holds the Pin in place of the entry with the same id, or at the end.

## Decisions

**D1 · The invalidation after a save** · Decides: Tech lead

The Spec names `invalidateQueries({ queryKey: ['pins'] })`. On `main`, the edit save adds a predicate that keeps `['pins', id, 'edit']` out (M2.15.2, #884 build). The edit panel is still mounted when the save ends. A plain call asks `/data/pins/{id}/edit` again, which sends the sources and the notes again. The test "does not ask again for the fields of the open edit panel" (NFR-10) proves this today. #884 Behaviour names the plain call too.

- **A.** Keep the predicate in `useWritePin`. The call still has `queryKey: ['pins']`, and each `['pins', id]` details query is stale. Cost: none.
- **B.** Use the plain call. Cost: one more request after each edit save, and the NFR-10 test goes.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D2 · How the server builds the `MapPin`** · Decides: Tech lead

The store saves a `Pin`. The span needs the birth and death of the Person. The point needs the Place.

- **A.** The action reads `tree.persons.get` and `tree.places.get`, then calls `spanOf` and `mapPins`. Cost: two reads by id for each save, and no store change.
- **B.** A new `PinGroup` method `getMapPin(id)` in both store adapters, with contract tests. Cost: about 150 more lines.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Alternatives considered

- Find the saved Pin in `tree.pins.list()`. This reads up to 10,000 Pins for each save, which the scale rule forbids.
- Build the `MapPin` on the client with `spanOf`: Spec D1 B, not chosen.
- Give `useAddPin` the write function as a prop from `MapWithPins`. The dev page `/screens/pin-form` then needs a stub too. A hook in `features/pins` needs no prop.

## Risks

- A Person or a Place that a save just used is missing when the action reads it. v1 deletes neither, so this is unlikely. `mapPinOf` gives `not-found`, and a test makes the store answer no Place. The form then shows its failed alert, and a repeat of the add returns the Pin saved first.
- A save while the first load of the Pins is in flight: `invalidateQueries` cancels that load and starts one more. The client then applies one list, which holds the Pin. The test "the Pins load once" covers a list that failed or has not started, where one request runs.
- The e2e Tree holds 9,995 seeded Pins and room for five more. The plan adds no save test, so the count of `e2e/pins.spec.ts` stays.
- Unlikely case (Spec): at 10,000 Pins, the next reload can drop a written Pin. No code; the Spec records it.

## Out of scope
