## Approach

The tech lead creates both Supabase projects, turns off sign-ups and the Data API, turns on automatic RLS on new tables, and sets the Vercel variables by hand; Claude has no Supabase or Vercel access. The build only changes `docs/repo-settings.md`: a new _Supabase_ table and one row per variable in the _Vercel_ table, written like the existing `KINSCAPE_GIT_READ_TOKEN` row. The names chosen here are the ones M2.3 (`env.ts`, `db:migrate`) and M2.5 (sign-in) read.

## Risks

- **Region.** Claude can't check whether Supabase offers Cape Town; the tech lead's comment in step 2 settles which one the doc records.
- **Direct connection.** On the free tier, Supabase's direct host may be IPv6 only. If the tech lead's network can't reach it, `DATABASE_DIRECT_URL` uses the session pooler instead, which also supports migrations; the doc says which.
- **Pausing.** Spec concern: an idle free project pauses. The _Supabase_ table notes that the tech lead resumes it in the dashboard.
- **Wrong scope.** A Production value in the Preview scope would put synthetic data next to the real Tree. The acceptance check below catches it.
