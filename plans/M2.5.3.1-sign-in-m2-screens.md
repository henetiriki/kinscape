# Plan: M2.5.3.1: Sign-in screens for M2

- **Spec:** #563
- **Requirement IDs:** [NFR-03](../docs/requirements.md#nfr-03)
- **Status:** approved

## Approach

Only a signed-in person can draw on the canvas, so most steps are the tech lead's; Claude does the rest and checks the result. The three boards in `design/canvas/export.json` keep their files and names and become the M2 version (Spec D1 A); copies with `-proposed` names keep today's content. Two new boards add the "can't sign in right now" state. The Screens table splits into an M2 table and a proposed one; `screenNames` reads rows from both, so no tooling changes.

## Components

What the boards draw, from the canvas's KinScape design system:

| Part                                               | Component                                       |
| -------------------------------------------------- | ----------------------------------------------- |
| Layout, hero                                       | `auth`: AuthLayout, SignInHero (drawn as today) |
| Email, password (with Show password)               | `forms`: TextField                              |
| Sign in                                            | `actions`: Button, L                            |
| Wrong password, can't sign in right now            | `feedback`: Alert                               |
| Keep me signed in (proposed only)                  | `forms`: CheckboxField                          |
| "or" divider, Continue with Google (proposed only) | Missing; stays hand-drawn (Spec Behaviour)      |

## Decisions

**D1 · The "can't sign in right now" Alert's tone** · Decides: Tech lead

The Spec says "the alert above the form, like the wrong-password error", but not its tone. M2.5.3.3 builds whichever is drawn, and only `error` gets `role="alert"`.

- **A.** `error`, like the wrong password: sign-in can't go ahead until the service answers.
- **B.** `warning`: nothing the user typed is wrong.
- **Other:** your own.

**Answer: A** (@henetiriki)

## Order of work

1. Record D1, then commit `plan(M2.5.3.1): approved by @<tech-lead>`.
2. Ask the tech lead in the PR to paste the design agent's prompt on the canvas, with D1's tone added, then to run the refresh steps and add the five `export.json` entries on this branch.
3. Read each changed board and check it against the Spec's Behaviour; list any mismatch in the PR for the tech lead to fix on the canvas.
4. Split the Screens table and set the test count. Push, then run the Design agent shots workflow (`gh workflow run design-agent-shots.yml --ref <branch>`), or ask the tech lead if that is denied.
5. Pull the shots commit, then run lint, `format:check`, `words`, the tests, `validate:boundaries`, `e2e` and `design:export` ("No snapshot changed"). Paste the output.

## Risks

- **Red until the shots commit:** the export test and `e2e` fail between steps 2 and 4; nothing is marked ready before then.
- **Board drift:** the design agent may move the layout or hero; step 3 compares each M2 and `-proposed` JPG with `main`'s and stops on any change outside the form.
- **Canvas access:** if `list_files` refuses, the refresh steps' fallback (a chat on the canvas) applies.
