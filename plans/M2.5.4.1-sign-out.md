# Plan: M2.5.4.1: Sign out

- **Spec:** #554
- **Requirement IDs:** [NFR-03](../docs/requirements.md#nfr-03)
- **Status:** approved

## Approach

Add `signOutAction` to `app/sign-in/actions.ts`, beside `signInAction`. It reads the session cookie, calls `endSession` (which ignores a malformed or unknown token), clears the cookie and redirects to `/sign-in`. It takes no arguments, so it trusts nothing from the client except the cookie, which `endSession` checks for format. Clearing uses a new `endedSessionCookie()` in `server/auth/sessions.mts`: the same name and attributes as `sessionCookie`, an empty value and `maxAge: 0`. A browser ignores a `__Host-` cookie that has no `Secure` and `Path=/`, and the docs don't say whether `cookies().delete()` sends them. Being a server action, it answers only POST, and Next.js aborts one whose `Origin` doesn't match `Host` (`node_modules/next/dist/docs/01-app/02-guides/data-security.md` › _Allowed origins_). So no CSRF code is needed.

## Decisions

**D1 · Where the action lives** · Decides: Tech lead

`features/` may not import `app/` routes, so where it lives decides how M2.5.4.4 (#572) reaches it from `Stage`.

- **A.** `app/sign-in/actions.ts`. `app/page.tsx` passes it to `MapShell` as a prop, beside the email #572 already passes.
- **B.** A new `'use server'` module, `server/auth/sign-out.mts`, that `features/map` imports directly. It would be the first server action outside `app/`.
- **Other:** your own.

**Answer: A** (@henetiriki)

**D2 · Session store down at sign-out** · Decides: Tech lead

The Spec doesn't say what happens if `endSession` throws.

- **A.** Let it throw: the cookie stays, Next.js shows its error page, and signing out again retries. The session is never left live while the user thinks it's ended.
- **B.** Catch it, clear the cookie anyway and redirect. The row stays valid until it expires (at most 30 days).
- **Other:** your own.

**Answer: A** (@henetiriki)

## Order of work

1. Test, then `endedSessionCookie`.
2. Tests for `signOutAction` against `memorySessions`: watch them fail on the missing behaviour, then write the action.
3. The e2e spec.
4. Lint, format, words, tests, `validate:boundaries`, e2e.

## Risks

- **Shared e2e session.** Every e2e project reuses one synthetic session (`e2e/auth.setup.ts`). Signing out ends it for all of them, so no e2e test here signs out. #572's sign-out test must sign in its own session first.
- **Nothing calls the action yet,** so no browser test runs it until #572. The unit tests run the real action against the memory session store.
