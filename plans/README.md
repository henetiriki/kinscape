# Plans

How plans are drafted, approved and committed. Start each one from [TEMPLATE.md](TEMPLATE.md).

1. <a id="draft-before-code"></a>**Draft before code.** Plan read-only: the files that change, the order of work, the risks, and how each acceptance check will be proven.
2. <a id="plans-committed-first"></a>**Spec plans are committed first.** Save the plan as `plans/<spec-id>-<slug>.md`. [`agent-approve.mts`](../scripts/agent-approve.mts) commits its approval as `plan(<spec-id>): approved by @<tech-lead>`; a plan committed by hand has `Status: approved` and that commit text. Spec ids look like `M0.1`; a Bug's is `B<issue number>`, and its plan is `plans/bugs/B<n>-<slug>.md`.
3. <a id="plan-pr-flow"></a>**In GitHub Actions**, first refresh the issue ([`refresh.md`](../.github/agent/refresh.md): any Drift means no PR, [stale-facts rule](#stale-facts)), then commit the plan as `plan(<spec-id>): draft` with `Status: draft` on `spec/<spec-id>-<slug>` (a Bug: `bug/<spec-id>-<slug>`; a Chore: `chore/<spec-id>-<slug>`), open a draft PR titled `<spec-id>: <Spec title> (plan)` (a Bug: `B.<n>: <title without "Bug: "> (plan)`) with `Closes #<issue>` in its body, and stop. Only the tech lead's approving review approves it; [`claude-build.yml`](../.github/workflows/claude-build.yml) first runs `agent-approve.mts`, which records the answers (`D1: B`) in the review or comments, or comments and stops if one is open. `@claude` comments are feedback: revise the plan only. If an answer changes a count, name or value in the Spec's Behaviour or Acceptance checks, reword only those lines in the Spec's issue body with `gh issue edit` (as [how we work](../docs/how-we-work.md#decisions) says) and note it in one line in the PR body. On approval, build, drop `(plan)` from the title, rewrite the PR body, and mark the PR ready. The title and body always describe the PR as it would merge now, not how it got there (except Evidence, [test-first rule](#test-first)); update both whenever the work changes.
4. <a id="chores"></a>**Chores.** Every chore is a Chore issue and commits `plans/chores/C<n>-<slug>.md`; [plans-committed-first rule](#plans-committed-first), [plan-pr-flow rule](#plan-pr-flow), [small-departures rule](#small-departures), [big-departures rule](#big-departures), [too-big rule](#too-big) and [approval rule](#approval) apply, with id `C<n>` and branch `chore/C<n>-<slug>`. The plan PR is titled `C.<n>: <title without "Chore: "> (plan)`; the build drops `(plan)`. The tech lead plans and builds a hand-back ([hand-back rule](#hand-back)). Only Dependabot's PRs, `actions-pin-update.yml`'s (head branch `bot/update-action-pins`) and reverts (head branch `revert-*`) need no issue or plan.
5. <a id="small-departures"></a>**Small departures** that don't change the plan's intent (file names, step order, an extra helper): update the plan in the same commit as the code, with one line under `## Deviations`.
6. <a id="big-departures"></a>**Big departures:** stop and return to planning if a change would alter scope, the data model, a public API, an acceptance check, or would add a dependency. The tech lead re-approves before work continues.
7. <a id="too-big"></a>**Too big:** if the plan won't fit its word budget, or the diff will pass the line cap in `/refine spec` › Step 1, stop, commit what works and ask the tech lead to split the Spec.
8. <a id="approval"></a>Tech lead's PR approval signs off code and final plan together.
9. <a id="missing-components"></a>**Missing components.** A screen plan has a `## Components` table (see the template). Build a missing component in the same Spec, in its own commit with its test, if the diff fits the size cap in the [too-big rule](#too-big). Otherwise stop: file a Spec for the component, set the screen Spec to `status: blocked` with "blocked by #<n>", and build no stand-in.
10. <a id="failing-tests"></a>**Failing tests.** Fix the code, not the test. Change, skip or delete a test, or loosen an assertion, only where the plan changes the behaviour it checks, listing that test under Files that change. Otherwise a wrong-looking test is a big departure ([big-departures rule](#big-departures)).
11. <a id="stale-facts"></a>**Stale facts.** Before drafting, refresh the issue as [`refresh.md`](../.github/agent/refresh.md) says (it decides whether to stop). Before building, check it against `origin/main`: the files, names, counts and linked issues it cites. Before either, check that a Bug still reproduces. If a check fails, stop: comment each mismatch (what the issue says, what the repo has), naming who fixes it; for the PO, swap the issue's status label for `status: ready-for-po`. Don't edit the issue, except as the refresh does.
12. <a id="test-first"></a>**Test first.** For logic a unit test covers, see the test fail on the behaviour (not an import error) before writing the code; paste that failing line in the PR's Evidence.
13. <a id="hand-back"></a>**Hand back, don't build.** A hand-back path matches a `.github/CODEOWNERS` line after the catch-all and isn't in `EXEMPT` ([`scripts/hand-back.mts`](../scripts/hand-back.mts)). If a plan edits one, [`claude-hand-back.yml`](../.github/workflows/claude-hand-back.yml) labels its PR `hand-back`. A chore needing a secret or too big ([too-big rule](#too-big)) gets no plan PR. With no plan PR, comment why on the issue.
